# mscz_webviewer

A browser viewer for MuseScore and MusicXML scores, powered by WebAssembly and rendered as SVG. Open a score, zoom in, and transpose the displayed notation without changing the original file.

This project uses substantial portions of [aria](https://github.com/hdi200/aria), which is based on MuseScore Studio, and additional code taken directly from [MuseScore Studio](https://github.com/musescore/MuseScore), including the MusicXML importer. Thank you to their authors and contributors.

## Use the viewer

1. Open the [live viewer](https://1921music.github.io/mscz_webviewer/) and wait for the engine to load.
2. Choose a score file, or drag and drop it onto the page.
3. Use the zoom and semitone transpose controls. Reset transposition to return to the original key.

**Keep original system breaks** is checked by default: transposition keeps the
original measures on each system and squeezes spacing when necessary. Very
crowded notation can overlap. Uncheck it to use normal automatic wrapping.
Page count can still change when transposition requires more vertical space.
Hosts can pass a third boolean to
`score.setViewTransposeSemitones(semitones, spelling, preserveSystemBreaks)`;
omitting it keeps the current setting (`score.viewPreserveSystemBreaks`).

Supported files: **`.mscz`, `.musicxml`, `.xml` (score-partwise), and `.mxl`**.

Scores selected from your device are processed locally in your browser; they are not uploaded to a server. The current interface includes Japanese labels. Optional GM playback provides play/pause/stop, master volume, and per-part volume, pan, mute and solo. Score editing is not included.

### Optional GM playback

The default build uses **EAS with its embedded 8-bit GM bank**. Set the CMake
cache string `MSCZ_PLAYBACK` to `OFF`, `EAS`, or `TSF_SF3`. Only the selected
backend is shipped. `OFF` removes the playback UI, timeline export, synth WASM,
worker and sound bank. `TSF_SF3` uses TinySoundFont with stb_vorbis and a bundled
SONiVOX-derived SF3 GM bank. Both online and standalone editions work without
contacting an audio service; the standalone HTML embeds all required assets.

In the WSL development environment, run from the repository root:

```sh
mise trust
mise install
MSCZ_PLAYBACK=EAS BUILD_DIR="$HOME/build/mscz-webviewer" mise exec -- bash scripts/build-wasm.sh
MSCZ_PLAYBACK=TSF_SF3 BUILD_DIR="$HOME/build/mscz-webviewer" mise exec -- bash scripts/build-wasm.sh
MSCZ_PLAYBACK=OFF BUILD_DIR="$HOME/build/mscz-webviewer" mise exec -- bash scripts/build-wasm.sh
```

Reconfiguration occurs on every invocation, so changing the backend works in
the same build directory. The output is `web/index.html` and
`web/index-standalone.html` below the selected build directory.

The top toolbar's `Playback panel` checkbox shows or hides the bottom playback and
mixer panel. It is checked by default and only appears in audio-enabled builds.
Hiding the panel does not stop playback or reset mixer settings.

Playback follows the displayed transposition, instrument pitches, repeats and
tempo changes through the existing MuseScore compatibility MIDI renderer.
Changing scores or transposition stops playback. Mixer settings survive display
transposition, but reset when opening another score. Multiple solo parts are
allowed; mute takes precedence over solo. Volume and pan initially come from
the score's primary instrument channel. Mixer changes take effect within the
short audio buffering window (normally less than half a second) and never
modify the score file. Chord-symbol accompaniment is generated by MuseScore's
MIDI renderer and appears as a separate `Part name: Chords` mixer row after the
instrument parts. Each chord row has independent volume, pan, mute and solo;
its initial instrument and levels come from the score's harmony channel.

This is GM playback, not Muse Sounds or a full desktop mixer. The backends may
sound different; reverb/chorus, runtime instrument editing and persistent
mixer presets are not implemented. Audio is synthesized in a worker, in short
buffers rather than allocating an entire song's PCM. Pause preserves both the
playback position and sustained voices. Very large scores can underrun on slow
devices. At most 128 mixer parts (including chord accompaniment) and 15 melodic instrument channels plus percussion
per part are supported.

Both synth adapters expose the same `synth_font/create/event/render/destroy`
interface. The worker owns one synth instance per score part (including drum
parts), so parts that share a GM channel can still be mixed independently.
Each render returns 256 stereo PCM frames at 44.1 kHz; the browser schedules
short buffers through Web Audio. The SF3 bank's decoded samples are shared
between its part instances. Backend-specific code stays in `src/synth/`.

Browser checks (all unexpected external requests are blocked and fail the test):

```sh
mise exec -- npm install
mise exec -- npx playwright install chromium
MSCZ_WEB_DIR="$HOME/build/mscz-webviewer/web" MSCZ_PLAYBACK=EAS mise exec -- npm run test:playback
```

Use the matching backend name for each build. `MSCZ_TEST_SCORE=/path/to/file.mscz`
adds an optional real-score smoke test; that score is not copied into the repo.

## One HTML file, including offline use

[Download the standalone HTML](https://github.com/1921music/mscz_webviewer/raw/refs/heads/main/docs/index.html), save it as `index.html`, and open it directly in a compatible browser such as Microsoft Edge. It also works offline over **`file://`**; no local web server is required.

The HTML contains the JavaScript, WASM engine, fonts, and other required resources. No companion files need to be downloaded. Open scores from your device using the file picker or drag and drop. Loading a score from a URL requires a network connection.

## Development

### PDF download

Use **Save PDF** to download all pages in the currently displayed key. Page
sizes and breaks come from the score, independent of screen zoom. Music symbols
remain vector paths; ordinary text stays searchable/selectable with embedded
font subsets and Unicode mappings. No score data is uploaded.

PDF export downloads pinned PDFKit 0.17.2 and SVG-to-PDFKit 0.1.8 browser scripts
from jsDelivr, with integrity checks, only when requested. Export fonts are also
downloaded on demand: Edwin (including bold/italic), the named music text fonts,
and Noto Sans JP as the Unicode fallback. No new runtime font binaries are
bundled. The default fallback may differ from an unavailable original typeface.
Missing glyphs fail export rather than silently saving empty text. Arbitrary
score images are not yet supported by PDF export.
Fallback is resolved for each text run, so a Japanese title does not replace
the music-text font used by chord symbols elsewhere on the same page.

The single HTML includes the export adapter but still needs an Internet
connection for its first PDF export, including when opened via `file://`.
Ordinary viewing/playback remains offline-capable. Successfully loaded fonts
and scripts are reused within the page; persistence across reloads is not
guaranteed. Failed downloads can be retried with Save PDF.

Hosts may import `FontResolver`, `embeddedFontProvider`,
`downloadFontProvider`, and `localFontProvider` from `web/font-resolver.js`.
Providers asynchronously accept `{ family, weight, italic, text, purpose }`
and return `{ family, bytes, format? }`, or `null` to delegate. `bytes` must be
readable font data (OTF/CFF and TTF are supported). Errors propagate; a resolved
font lacking required glyphs delegates to the next provider. CSS-only access
to an OS font is insufficient for embedding. `localFontProvider()` explicitly
requests browser Local Font Access in a supported secure context and may need
user permission; the viewer never requests this automatically.

```js
import { FontResolver, embeddedFontProvider, defaultFontResolver } from './font-resolver.js'
import { scorePdf, downloadScorePdf } from './pdf-export.js'

const fontResolver = new FontResolver([
  embeddedFontProvider(hostFontData), // e.g. Rostrum's lazy font byte map
  ...defaultFontResolver().providers
])
const pdf = await scorePdf(score, { fontResolver }) // application/pdf Blob
// Or downloadScorePdf(score, { fontResolver, filename: 'score.pdf' }).
```

This is an opt-in host API: importing the score engine alone does not load
export adapters or PDF libraries. Rostrum does not gain a new PDF control.
Browser tests mock every external PDF/font request with local assets, verify
Japanese text extraction, subset embedding, multipage dimensions, HTTP/file
delivery, retry and host-provided fonts. Run against a generated web payload:

```sh
MSCZ_WEB_DIR=/path/to/build/web mise exec -- npm run test:pdf
```

The C++ rendering core is adapted from aria and MuseScore Studio. This project removes the Qt dependencies from the upstream rendering code so that the core can be compiled to WebAssembly without Qt. The web interface lives in [`web/`](web/), the browser integration in [`src/`](src/), and build and verification scripts in [`scripts/`](scripts/).

For build instructions, architecture, provenance, benchmarks, and implementation history, see [Development notes](DEVELOPMENT_NOTES.md). These notes include historical plans and machine-specific paths. GitHub Pages serves the checked-in standalone HTML from `main` → `/docs`.

## Embedding in Rostrum

Rostrum consumes this repository as a pinned Git submodule. Its UI and packaging
remain in Rostrum; the shared engine exposes these additional, opt-in APIs:

- `score.rostrumInfo()` returns page dimensions and musical-time/staff anchors,
  Rostrum settings and annotation SVG placements. It also hides Rostrum annotation
  images in this session so the host can draw editable overlays. Ordinary viewer
  opening/rendering never invokes this method.
- `score.saveRostrum({ settings, annotations })` returns MSCZ bytes, rebuilding
  from the original input in the original key. It does not alter the current view
  or source bytes. `settings` is a JSON string; annotation positions and sizes are
  expressed in staff-space units relative to the anchors above.
- `engine.textFonts.svgFontCss(svg)` supplies embedded font CSS for raster/export
  consumers. On-screen pages continue to share the registered FontFace objects.
- `playbackAssets.workerURL` optionally selects a packaged module worker, for
  example under a browser extension CSP. Without it, existing HTTP and embedded
  worker loading is unchanged.

The standalone viewer does not expose annotation editing or saving controls.
Its existing open, zoom, transpose and optional playback behavior is unchanged.
The browser suite covers both the viewer lifecycle and opt-in save/reopen across
HTTP and offline standalone builds, including playback-disabled builds.

### Playback tracking API

`score.playbackTimeline()` also returns `visual: { version: 1, notes, systems }`.
`notes` contains `{ id, start, end }` intervals in playback seconds, with repeats
expanded. Intervals follow written note durations (including tied continuations),
not reverb, pedal tails or articulation shortening. Grace notes use their actual
MIDI renderer timing; zero-length renderer events are omitted. `systems` contains
`{ id, page, start, end, bounds: [x, y, width, height] }`; `page` is zero-based
and bounds are fractions of the page, independent of SVG DPI and host zoom.
System intervals include rests. IDs are session-local and must be refreshed
after replacing the score or changing its layout/transposition; never persist them.
SVG notehead groups carry the matching `data-note-id` attribute.

The exports in `web/playback.js` are reusable by embedded hosts:

- `playbackPosition(timeline, seconds)` returns `{ time, noteIds, system }`.
  Intervals include their start and exclude their end. It has no DOM or audio dependencies.
- `player.tracking` returns the same snapshot, clearing it when stopped.
- `player.subscribe(callback)` observes transport/position changes alongside the
  existing constructor callback and returns an unsubscribe function.
- `new PlaybackView(player, { getPages, onSystem })` colors the SVG noteheads
  supplied by `getPages()` and calls `onSystem(system)` when the playing system
  changes. The host owns scrolling and page mounting. Call `update()` after
  rendering/mounting pages, `resetFollow()` to follow the current system again,
  and `destroy()` to unsubscribe and remove highlighting.

PlaybackView uses a temporary CSS class; source colors, annotations and exports
are unchanged. Pausing retains the current highlight. Auto-scroll is optional
in both the standalone viewer and Rostrum. The tracking API has no annotation
visibility side effects and does not call `rostrumInfo()`.

The current system's `anchors` are `[playbackSeconds, pageXFraction]` pairs.
`playbackPosition()` and `player.tracking` also return `cursor` (or `null`), with
`{ page, x, y, height }` in page fractions. The cursor interpolates continuously
between engraving positions, including rests and tempo boundaries; pauses hold
its position. Repeats and page/system changes jump to the new score position.
`PlaybackView` draws a red, system-height SVG line at display refresh rate using
the audio clock, while preserving red noteheads. Pause holds both; stop hides both.
Hosts supplying a subset of mounted SVG pages must set `svg.dataset.playbackPage`
to the zero-based source page index. Cursor elements are transient overlays and
are removed by `destroy()`; they are never added to score files or export SVGs.

### State-preserving seeking

The footer always shows `|<`, the full-song seek slider and the clock to the
right of Volume. The slider, beginning button and notehead taps work while
playing or paused and retain the previous transport state. Dragging previews
silently until release; a playing gesture resumes automatically, while a paused
gesture stays paused. Note taps commit on release and ignore moved pointers.
Repeat visits are preserved where possible. Mixer
opens a nonmodal dialog, initially closed.

Shared Playback APIs:

- `cue(seconds = 0)` activates a stopped score at a silent paused position,
  without requesting host scrolling. It also works while paused.
- `seek(seconds)` returns false outside an active transport, clamps to
  `[0, duration]`, clears queued audio/voices and updates tracking immediately.
  It resumes asynchronously if previously playing (including a pending resume).
- `canSeek` reports whether playback controls are active.
- `beginScrub()` / `endScrub({ cancel })` hold a silent preview and restore the
  previous transport state on release. Cancellation restores the original time;
  Stop/score changes invalidate pending resumes.
- `seekNote(noteId)` selects the note's start in the current repeat `visit`,
  falling back to the nearest occurrence if absent from that visit.
- `PlaybackView.noteAt(clientX, clientY, svg)` hit-tests noteheads with a small
  touch margin and returns an ID during active playback. Hosts decide how to consume taps.
- `PlaybackView.bindSeek(range, rewind)` binds pointer, keyboard and accessibility
  input to the shared transport behavior and returns an unbind function.
- `onSystem(system, { seeking })` is also called on explicit seeks while paused;
  hosts should reveal the destination even when automatic following is disabled.

Seeking reconstructs instrument/controller/pitch-bend state lazily on Play,
without replaying earlier note attacks or sustained voices. Attacks exactly at
the chosen timestamp remain queued. Ordinary pause/resume without seeking still
preserves buffered audio and held voices. Position, highlights, cursor and seeks
are presentation state, never score edits.
